# Application behavior

Agents App has one main window and a Settings window. Its navigator selects a user or project scope and a configuration page; the inspector shows the current selection. It uses Core’s public manifest, skill, instruction and combined update APIs directly.

## Prompt audit

Open **Diagnostics → Audit Prompts** to scan the selected project or user scope. **Choose File** inspects one prompt in that scope. Findings show their location, severity and reason. Export the same report as Markdown, JSON or SARIF.

For a text prompt with removable characters, choose **Review Character Removal** to inspect the code points and their positions. **Apply** removes the displayed characters if the file still matches the preview, then scans the file again.

## Configuration and preferences

Core owns declaration parsing, defaults, managed state, source/resource provenance, deployment diagnostics and recovery. The main inspection returns one immutable generation containing the document, full typed declaration, managed components, sources, groups, resources, deployments, subscriptions and actual read locations. Browsing does not initialize configuration. Missing manifests, invalid manifests, orphan state, recovery pending and unavailable roots remain distinct. Supplemental own-instruction and cross-project mapping reads have separate admission and do not claim an atomic cross-project snapshot.

The app stores registered project directories, last selected scope, inspector visibility and the assistance preference in its own UserDefaults domain. Adding a directory does not create configuration; removing one does not delete configuration. The app does not use a credential store. Browsing does not start configured executables; an explicit managed MCP connection test can start its owned command or connect to its endpoint. A moved, missing, unreadable or non-directory project root stays registered and is presented as unavailable, rather than as an existing empty scope. Restoring the directory and refreshing rereads it.

Native FSEvents monitor Core-owned read dependencies from the inspection and supplemental operations. Mapping and managed MCP provide typed entry and subtree interests. Entry interests match the same path or an ancestor, covering admission, absent-path creation and atomic replacement; subtree interests also match descendants. Independent subtree interests remain recursive when an entry names the same path. Other flat producers, including source/resource reads, are explicitly lifted to subtrees. Existing ancestors determine stream registration. The stream requests IgnoreSelf for contemporary events and retains historical events from the captured read boundary; owned writes explicitly refresh after their outer terminal. Events only invalidate reads and previews and queue a fresh read. They never apply configuration or update a subscription. Streams are released when the scope is left or quit begins. A failed initial read still monitors Core-owned state locations, so correcting an invalid declaration can recover automatically. A stream failure reports a diagnostic and leaves manual Refresh available.

Refresh retains a selected NodeID only if it still exists in the new immutable document; it never maps a stale node by array index. External changes retain an open draft and its original nodes, mark it stale and clear transient preview bindings. Explicit re-review retains those nodes only if Core’s document digest is identical; a changed declaration requires a fresh draft. Changes during apply wait for the owned Core terminal before refreshing. Manual refresh and application activation remain available. Source subscription baselines are recorded state, not an automatic subscription update.

Paths use compact scope-relative presentation where possible. Full paths remain available through help, accessibility and explicit copy actions. The inspector omits synthetic defaulted fields using Core’s source-map evidence, while retaining authored empty collections and explicit native null values. Technical declaration coordinates and document digests are contextual copy actions.

## Agent Clients settings

ClientSettingsModel holds passive AgentClientOperations inspection results in memory. Detect Clients and Detect Again explicitly run on the existing serial executor and application operation registry. The result shows the captured user context and observation interval, command roles and selected/resolved paths, application observations, raw versions and builds with provenance or typed unknown reasons, supplied PATH coverage and exclusions, configuration locations and frozen schema evidence. Historical evidence revisions remain distinct from observed versions; configuration preview owns admission.

Detection never invokes clients or version commands. Core owns command candidates, path resolution, metadata recipes and evidence. Settings provenance paths do not enter workspace monitoring, freshness, recovery or editing availability. Superseded requests cannot replace the latest Settings result. Queued cancellation still delivers a terminal; running synchronous inspection stays owned through return, including on quit. Workspace selection does not change the captured user context shown in Settings. Native passive-observation acceptance remains with the delivery owner.

## Cache settings

Settings → Cache shows the location and size of the shared Git, HTTP and deployed-file caches. Prune selects Git groups by age. Clean selects entries in all three stores. Review the selected entries and their sizes before confirming removal. The result shows the space reclaimed and identifies entries that were skipped or failed.

## Client backups

Backups is available from the sidebar regardless of the workspace’s selected scope or read status. Back Up captures the selected clients, optional registered projects and output folder. Core’s `ClientBackups.create` runs once per client on the app’s serial worker. The form reports each actual package path or individual failure. An empty project selection still includes local sessions and user configuration. Backup packages can include credentials already stored in the backed-up files.

Restore Package opens one archive and asks Core to inspect it. Original project roots are shown beside editable local destinations. An original directory that still exists is suggested as its destination. Review Restore passes the displayed mapping to Core and shows its file paths and change kinds, with replacements first. Changing a destination clears the review. The table displays paths and change kinds only. Before restoring file changes, quit the client named in the review. Restore submits the exact reviewed Core preview on the serial worker. The app waits for the operation to finish before releasing it and then refreshes the configuration view. Core owns package validation, destination checks and file writes.

## Explicit content actions

Sources offers **Export Component Inventory** for the selected scope. The save panel writes a CycloneDX 1.6 JSON file containing locked source versions, component names, kinds and target clients from the displayed inspection.


Creating a local skill requires choosing its directory. Project instructions are available only in a project scope. A serial worker asks Core for InitializationDescription; confirmation shows Core's exact file, requested scope/name and starter template. The immutable description owns an existing-root identity, not a live lock or borrowed source handle. Confirmation submits that same description to UpdateOperations.initialize. Its typed outer disposition and recovery/cleanup outcome enter the existing application operation registry before selection filtering. These actions create starter content only and do not install it or edit configuration. App preflight rejects a known unavailable registered root; Core owns the publication identity precondition. Full production failure-path and selected-directory acceptance remain required.

Subscriptions use Core previewAdd/previewRemove and immutable WatchMutationPreview, followed by performWatch on the serial worker. Preview displays the source identity and captured baseline. Confirmation never calls a second writer inside UpdateOperations.perform. Removal preserves source declarations and installed content. Check Updates explicitly reads all subscription statuses; View Changes reads one source's typed diff. The result shows recorded/current baselines and actual before/after text, executable flags, link destinations or binary sizes. These reads never deploy or mark a baseline as read, and retain original-scope errors after selection changes. Status and diff retain their durable read footprints, including absent state leaves for an empty subscription list. Mark Displayed Content as Read submits the exact displayed WatchStatus to UpdateOperations.performWatch; Core revalidates its captured scope, state and content. The application owns acknowledgment through its actual disposition, recovery and cleanup before refreshing. Native acceptance remains required.

Import explicitly selects a supported pinned format, input file and optional authoring root. SourceImportOperations.inspect returns immutable adapter-issued availableChoices, complete effects and fixed contributions, supported requiredInputs, producer claims, hashes, diagnostics and binding requirements. Choices retain their opaque owner IDs; one choice includes every family controlled by its producer key. The app supplies no arbitrary producer keys or installed-skill names.

Choose Specific Producer Entries distinguishes keeping the current selection from an explicit empty selection. Empty import selection retains the adapter's own fixed effects and empty-selection meaning. Inspect Again restores the adapter's initial omitted selection. Supported typed inputs accept Git coordinates, input-root-relative independent content, or symbolic environment/secret reference names. They accept no credential values. Resolve Selection and Inputs calls the current inspection's resolving method on the serial worker, then replaces it with the returned inspection and its new handles. Pending form changes cannot review the previous conversion. Every public diagnostic and unresolved requirement remains visible.

Selected preserved resources requiring a binding rewrite keep Review disabled with a correction path: correct the source or independent content and inspect again. Resolving a canonical symbolic slot does not rewrite raw files or clear their independent admission. Core's updateRequest and preparation retain final admission, integrity and standalone-source checks. The captured request enters ordinary preview, reprepare, displayed-fingerprint comparison and apply. Import never grants ownership by copying an installed tree. Input edits clear the prior inspection and handles. Scope changes, cancellation and obsolete completions retain the existing application operation ownership and freshness rules.

Managed MCP tests start from an exact ComponentSelection; snapshot construction runs on the serial worker, closes Core's borrowed scopes and returns an opaque immutable snapshot. Describe metadata and explicit process/network effects precede the user action. One-time binding bytes are cleared from presentation on admission. The async public test runs off MainActor, in the same application operation registry used by other tasks. Cancellation and scope changes retain ownership through the actual resource-cleanup result; obsolete tools do not replace current selection and cleanup errors remain original-scope diagnostics. Tests do not invoke business tools. Confirmation displays Core’s safe executable, individual ordered arguments and working directory, including captured-content indicators, or its redacted endpoint. The snapshot’s durable readDependencies join workspace invalidation: live resources contribute logical and resolved entry interests, while managed source interests retain their independent subtrees. Captured resources expose no borrowed staging paths. The description is presentation data; execution uses the original opaque snapshot. Actual transport/cleanup and GUI acceptance remain required.

Named prompt preview calls Core’s renderer. Core owns locked section order and append semantics; the app does not render or append text itself. The app displays returned UTF-8 text and copies it only on explicit action. Instruction mapping export always includes user scope and the selected registered projects, including Core’s missing or unavailable status for each scope. A registered project directory observed as unavailable is reported with its path diagnostic rather than as an empty mapping. Mapping dependencies join workspace invalidation for every status, including absent, failed and external recovery anchors and Core-admitted logical/physical root aliases. Mapping reads are not an atomic cross-project snapshot.

Declaration forms use public typed manifest values for defaults, sources, components, groups, uses, instruction exports and structural move/remove intents. Component forms cover skills, instructions, MCP servers, hooks, subagents, commands, language servers, permissions, ignores and plugins. Ordered collections preserve order and editable row identity; omitted, empty and explicit-null values remain distinct where the public type supports them. Native decimal text remains exact. Skill forms optionally narrow discovery with a search path relative to the selected source’s discovery root. Executable forms optionally specify a source alias independently of the working-directory source. Both fields preserve omission and the complete typed value through editing and review; Core owns coordinate validation. Executable arguments use ordered individual rows: empty strings, duplicates and embedded line breaks are preserved. Native object forms allow empty-string keys and prevent duplicate insertion from overwriting values.

Drafts are held in memory. Existing component, source, group and group-reference forms load typed values from the same inspection as their document nodes. Component replacement and structural edits use those exact nodes. Existing source forms replace the exact source NodeID from their captured document; Core preserves its position and rewrites typed alias references, including executable and working-directory sources. New sources upsert a named declaration. Group forms upsert the named declaration; an explicit group-name change removes the original name in the same typed edit request. Group references retain their conditions, symbolic source/group use, container and order. Structural controls remove sources, groups and references or move components/references within or between containers. Ordered instruction sections, including named prompt sections, support exact-node move/removal; the instruction form also inserts and edits sections and prompts. Export rows preserve order and individual values. Core rejects invalid dangling references or unsupported edits. Existing documents submit typed edits with their captured digest; first configuration submits a typed declaration with an absent-document precondition. Core owns validation, formatting, comments and publication. The app never writes prepared document bytes.

User-scope instruction declarations can explicitly select Antigravity as an installation target. Each ordered section’s recipient condition can narrow the same target selection. Add from Source offers Antigravity when the selected units are user-scope instructions. Core resolves the selection and prepares one Antigravity Markdown file per selected instruction unit, alongside the existing targets for other clients.

Review Changes prepares a real combined report. The Instruction Files table shows each installation path, proposed change, verification against the previous lock, and proposed byte count. Selecting a row shows Core’s captured before and after text and the recipients. The review displays Core’s shared Antigravity token budget advisory. Core reports blocking conflicts and oversized rules through the review and its diagnostics. Installed Antigravity Rules in the Instructions page shows the current verification from the Core inspection. The review also shows skill file/membership changes, named prompts, and native change names/targets, recipients, required binding names, resources and file-access changes. Core’s human-readable symbolicBefore/symbolicAfter text appears directly under Before and After. Missing text is labelled unavailable. The App does not decode internal NativeValue serialization. Confirmation captures that request and fingerprint, then enters a new synchronous Core operation that prepares again and applies only if unchanged. Scope switching and a second write are disabled from confirmation through the outer terminal. A rejected preview or apply retains diagnostics and the draft. A committed outcome is shown explicitly even when cleanup also reports an error; it is not offered an ordinary retry. Closing the result after commit dismisses the completed draft.

The Changes page offers full update, precise component update/removal using the inspection’s generation-bound selections, and one full locked restore. It does not choose components by ambiguous display names. Core checks producer ownership and selection editability. Add from Source captures an explicit alias and SourceDeclaration, including requirement and search path. A declared source can populate those coordinates. UpdateOperations.inspectSource returns Core's available selection units, full linked/adapter effects, provenance, conditions, recipients, source constraints, unavailable reasons and supported input handles. The UI uses opaque IDs, not labels or parsed producer names. Native registration is an indivisible unit with Core's captured single recipient; components strategy exposes full containers and typed member choices. Symbolic exported groups remain symbolic additions. Options use existing agent, condition and skill-mode values. Optional explicit adapter/document coordinates use the same finite import profiles and typed input forms.

Review Selected Addition calls catalog.select on the serial worker and submits its captured updateRequest through the ordinary review/apply flow. An empty new-catalog selection creates no request or state. Changed source/destination evidence and foreign handles are rejected. App neither subsets displayed records to construct intent nor implements linking. Review Declared Sources remains a separate whole-authored-selection action; authored NodeID editing and the Changes page's full update/restore actions retain their existing meanings.

If the preview requires runtime bindings, the confirmation sheet accepts explicit one-time secure inputs, including an intentionally empty value. The immutable input bytes go to Core’s sole synchronous provider during this apply. They are cleared from presentation state on admission, retained only by the owned worker call, and released on completion. They are not written to preferences, diagnostics, inspection or a credential store. Core owns private materialization and file permissions.

Recovery pending disables ordinary modification. Recover and Recheck explicitly enters Core’s writer/recovery boundary without applying new configuration. Recovery and cleanup status remain attached to the original scope, including failures before a callback. A later verified Core observation can resolve Core recovery blocking while retaining the historical diagnostic. The app does not inspect transaction journals or recover another project by interpreting paths.

## Operation lifetime

The application owns a MainActor observable model independently of views. It registers every read, creation, rendering, discovery, preview, apply and recovery operation before admitting it to a serial background OperationQueue. Explicit asynchronous assistance and MCP testing are registered in the same application operation table and retain their Tasks until the actual call and cleanup return; it does not occupy Core’s synchronous queue. Core’s synchronous outer call returns before its completion is delivered to the model. No prepared handle or borrowed source path is retained across actor boundaries.

Cancellation skips queued work while preserving terminal delivery. A running synchronous call remains owned until it returns. A thread-safe admission check immediately before apply linearizes cancellation against starting apply; once apply starts, the app waits for Core’s result. Changing selection invalidates its presentation; diagnostics are still processed against the original scope before the operation is removed. An actual creation result remains attached to its original request. Declaration selection and structural drafts use Core node identities belonging to the captured document generation.

Normal quit and last-window closure go through an AppKit termination delegate. Quit stops admission, cancels queued work and returns `terminateLater` while any operation remains. The delegate replies only after terminal processing. A reported cleanup failure cancels quit and remains visible in diagnostics. Disposition, pre-callback recovery and pending cleanup are processed before selection-generation filtering. Recovery observations are ordered by operation admission so a late older completion cannot clear a newer pending status. The app does not infer transaction state from error text.

## Packages and source policies

Choose a scope in the sidebar. In Components, open **Browse MCP Registry** to search the public registry or enter a private registry URL. Select a server, choose its connection, supply any input mappings, and review the installation for the selected clients. Private registry tokens are held in the open sheet.

In **Packages → Create Bundle**, select installed instructions, skills and MCP servers, enter a package name and version, then export the file or publish it to a team directory. Skills include their directory contents. Add package dependencies with an exact version, a compatible major or minor version, or a range with an exclusive upper bound. Each dependency uses the publishing marketplace by default and can select a Git repository or an HTTPS index for packages from another marketplace.

In a project, **Packages → Package Project** lets you choose local instructions, complete skill directories, MCP servers and locked components before installation. Review the included paths, integrity findings and digest before exporting or publishing. When the project contains an author specification, **Review Project Specification** uses its selections. The format picker also supports exporting a native plugin directory.

Choose **Save to Lock** after assigning package members to clients to review the versions and recipients for deferred deployment. **Save Lock** records them in this scope. Open **Manage Packages → Review Offline Deployment** to review and apply the native file changes from that lock.

Open **Packages → Manage Packages** to browse a saved marketplace, choose a directory, browse a Git repository or open a local bundle. A bundle with package dependencies must be published to a marketplace for installation. Select a marketplace release and choose **Inspect Package**. Adjust its version requirement if needed, resolve the graph and choose clients for components of the package and its reachable dependencies. Each root has its own client selections. **Resolve and Lock Only** keeps the draft selections available when switched off and prepares a root with no client assignments.

After reviewing a project package, choose **Publish → Stage for HTTPS Hosting** and select a directory to generate or extend its static index. Host that directory at the team’s HTTPS endpoint.

To connect a static team catalog, open **Packages → Marketplace → Add HTTPS Marketplace** and enter its name and index URL. Choose the user scope to register a private catalog and enter its access token. Projects can open this registration from the Marketplace menu. **Set Access Token** reconnects a registered index with a token for the open Packages sheet. If an archive uses a CDN, enter its HTTPS origin under **Trusted Download Origins**.

**Save Marketplace As** records the name in Core’s marketplace directory for the selected scope. Projects can browse user registrations and override them with a project registration of the same name.

**Installed Packages → Check for Updates** shows the locked release, the release eligible under the current graph constraints, and the latest published release. Choose **Review Update** to see proposed changes to releases, client selections and other affected roots. **Review Removal** shows the effect of removing one root, including retained contributions from other roots. The app applies the checked Core preview through the same review and apply flow as other configuration changes. Use **Changes → Preview Restore** to restore from the scope’s lock.

In Sources, choose **Edit Source Policy** to configure the selected scope and inspect inherited rules. The organization policy can be supplied via `AGENTS_ORGANIZATION_SOURCE_POLICY`. Project installs must satisfy the organization, user and project layers that are configured. **Export Component Inventory** saves a CycloneDX JSON inventory from the current inspection.

Select a declared source in either scope to see **Source Access** in the inspector, including sources that have never been installed. The offline report shows Core’s effective host, provider, transport, credential category and availability under the scope’s source policy. **Validate Source** explicitly asks Core to verify an available direct HTTPS credential when its trusted binding authorizes the provider’s identity endpoint. The result is Accepted, Refused or Inconclusive. Selecting another source, hiding the inspector or refreshing clears the result and cancels pending admission. Cancel Validation also clears the pending result. An admitted synchronous check remains owned through Core’s return.

## On-device assistance

Settings offers an opt-out preference and displays actual SystemLanguageModel availability on macOS 26 or later. Actions are hidden when disabled or unavailable. A selected managed skill’s public name and description can be explained or translated. A reviewed Core update can be summarized or its configuration changes explained. The change projection includes structural facts only: counts, kinds, missing-state reconstruction and access-change/binding-slot counts. It excludes native values, file contents, paths, source URLs, prompt bodies, binding names and runtime inputs.

Each action first displays its complete selected input for review. Translation accepts an explicit target language. Oversized input is refused before generation. Generate creates one independent on-device LanguageModelSession, with no tools, transcript persistence, chat or cloud fallback. Output is auxiliary selectable/copyable text and never feeds an edit or apply API. Model errors use a fixed safe diagnostic because provider errors may quote input. Cancellation, opt-out, scope changes and quit request Task cancellation but keep ownership until the actual generation returns. Obsolete output is withheld while its safe original-scope failure remains recorded.

The framework is weak-linked for the macOS 15 deployment target and used only behind macOS 26 and system-model availability checks. The user performs final native acceptance on the current Mac. The implementation follows [Apple’s single-turn session guidance](https://developer.apple.com/documentation/foundationmodels/generating-content-and-performing-tasks-with-foundation-models).

## Development validation

The shared scheme isolates its test host through explicit Debug-only test inputs and in-memory preferences. A Debug launch may also supply `--agents-fixture-root <absolute-directory>`; that directory contains `home` and `project` subdirectories prepared by the developer. The launch input does not create fixtures. Release builds ignore these inputs.

Unit tests exercise operation ownership and quit decisions with controlled worker and cleanup timing, stale-selection diagnostics, real Core reads, invalid/orphan configuration, no-write browsing, fixture-only creation and overwrite refusal, real prompt rendering and mappings, typed edit/preview/apply, fingerprint rejection, full restore, source discovery, ephemeral runtime input, source-map presentation, real file-event invalidation and assistance ownership/privacy projection. Unconditional integration failures remain acceptance blockers. UI acceptance uses the designated computer-use surface; the UI-test target is present without a second automation implementation.
