# Application behavior

Agents App has one main window and a Settings window. Its navigator selects a user or project scope and a configuration page; the inspector shows the current selection. It uses Core’s public manifest, skill, instruction and combined update APIs directly.

## Configuration and preferences

Core owns declaration parsing, defaults, managed state, source/resource provenance, deployment diagnostics and recovery. The main inspection returns one immutable generation containing the document, full typed declaration, managed components, sources, groups, resources, deployments, subscriptions and actual read locations. Browsing does not initialize configuration. Missing manifests, invalid manifests, orphan state, recovery pending and unavailable roots remain distinct. Supplemental own-instruction and cross-project mapping reads have separate admission and do not claim an atomic cross-project snapshot.

The app stores only registered project directories, last selected scope, inspector visibility and the assistance preference in its own UserDefaults domain. Adding a directory does not create configuration; removing one does not delete configuration. The app does not use a credential store. Browsing does not start configured executables; an explicit managed MCP connection test can start its owned command or connect to its endpoint. A moved, missing, unreadable or non-directory project root stays registered and is presented as unavailable, rather than as an existing empty scope. Restoring the directory and refreshing rereads it.

Native FSEvents monitor the immutable inspection and supplemental own-instruction, prompt-export, preview, initialization, import and subscription read locations. The stream excludes this process’s own changes; owned writes explicitly refresh after their outer terminal. Existing ancestors cover creation of absent paths and atomic replacement; source/resource directory descendants invalidate their scope. Events only invalidate reads and previews and queue a fresh read. They never apply configuration or update a subscription. Streams are released when the scope is left or quit begins. A failed initial read still monitors Core-owned state locations, so correcting an invalid declaration can recover automatically. A stream failure reports a diagnostic and leaves manual Refresh available.

Refresh retains a selected NodeID only if it still exists in the new immutable document; it never maps a stale node by array index. External changes retain an open draft and its original nodes, mark it stale and clear transient preview bindings. Explicit re-review retains those nodes only if Core’s document digest is identical; a changed declaration requires a fresh draft. Changes during apply wait for the owned Core terminal before refreshing. Manual refresh and application activation remain available. Source subscription baselines are recorded state, not an automatic subscription update.

Paths use compact scope-relative presentation where possible. Full paths remain available through help, accessibility and explicit copy actions. The inspector omits synthetic defaulted fields using Core’s source-map evidence, while retaining authored empty collections and explicit native null values. Technical declaration coordinates and document digests are contextual copy actions.

## Explicit content actions

Creating a local skill requires choosing its directory. Project instructions are available only in a project scope. A serial worker asks Core for InitializationDescription; confirmation shows Core's exact file, requested scope/name and starter template. The immutable description owns an existing-root identity, not a live lock or borrowed source handle. Confirmation submits that same description to UpdateOperations.initialize. Its typed outer disposition and recovery/cleanup outcome enter the existing application operation registry before selection filtering. These actions create starter content only and do not install it or edit configuration. App preflight rejects a known unavailable registered root; Core owns the publication identity precondition. Full production failure-path and selected-directory acceptance remain required.

Subscriptions use Core previewAdd/previewRemove and immutable WatchMutationPreview, followed by performWatch on the serial worker. Preview displays the source identity and captured baseline. Confirmation never calls a second writer inside UpdateOperations.perform. Removal preserves source declarations and installed content. Watch status/diff/seen interaction remains separate pending work.

Import explicitly selects a supported pinned format and input file. SourceImportOperations.inspect returns captured metadata, producer claims, observed hashes, diagnostics and binding requirements without deploying. The app displays those values and requests Core's captured updateRequest against the immutable scope inspection on its worker. Subsequent review/apply uses the existing fingerprint and outer transaction path. Core rejects unconverted requirements, conflicting aliases, changed inputs and imports lacking independent authoring authority. App does not copy an installed tree to grant ownership or parse foreign configuration itself. Additional source/binding/selection resolution UI remains to complete the broader import workflow.

Managed MCP tests start from an exact ComponentSelection; snapshot construction runs on the serial worker, closes Core's borrowed scopes and returns an opaque immutable snapshot. Describe metadata and explicit process/network effects precede the user action. One-time binding bytes are cleared from presentation on admission. The async public test runs off MainActor, in the same application operation registry used by other tasks. Cancellation and scope changes retain ownership through the actual resource-cleanup result; obsolete tools do not replace current selection and cleanup errors remain original-scope diagnostics. Tests do not invoke business tools. Core still needs to expose a safe command/argv/cwd or redacted-endpoint description and snapshot read footprint for the complete accepted confirmation interface. Actual transport/cleanup and GUI acceptance remain required.

Named prompt preview calls Core’s renderer. Core owns locked section order and append semantics; the app does not render or append text itself. The app displays returned UTF-8 text and copies it only on explicit action. Instruction mapping export always includes user scope and the selected registered projects, including Core’s missing or unavailable status for each scope. A registered project directory observed as unavailable is reported with its path diagnostic rather than as an empty mapping. Mapping reads are not an atomic cross-project snapshot.

Declaration forms use public typed manifest values for defaults, sources, components, groups, uses, instruction exports and structural move/remove intents. Component forms cover skills, instructions, MCP servers, hooks, subagents, commands, language servers, permissions, ignores and plugins. Ordered collections preserve order and editable row identity; omitted, empty and explicit-null values remain distinct where the public type supports them. Native decimal text remains exact. Executable arguments use ordered individual rows: empty strings, duplicates and embedded line breaks are preserved. Native object forms allow empty-string keys and prevent duplicate insertion from overwriting values.

Drafts are held in memory. Existing component, source, group and group-reference forms load typed values from the same inspection as their document nodes. Component replacement and structural edits use those exact nodes. Source/group forms upsert the named declaration; an explicit name change removes the original name in the same typed edit request. Group references retain their conditions, symbolic source/group use, container and order. Structural controls remove sources, groups and references or move components/references within or between containers. Ordered instruction sections, including named prompt sections, support exact-node move/removal; the instruction form also inserts and edits sections and prompts. Export rows preserve order and individual values. Core rejects invalid dangling references or unsupported edits. Existing documents submit typed edits with their captured digest; first configuration submits a typed declaration with an absent-document precondition. Core owns validation, formatting, comments and publication. The app never writes prepared document bytes.

Review Changes prepares a real combined report. It shows skill file/membership changes, instruction targets and named prompts, and native change names/targets, recipients, required binding names, resources and file-access changes. Internal encoded NativeValue wrappers and format/ownership labels are not product preview text. Core must supply human-readable symbolic before/after output; App does not decode that internal encoding. Confirmation captures that request and fingerprint, then enters a new synchronous Core operation that prepares again and applies only if unchanged. Scope switching and a second write are disabled from confirmation through the outer terminal. A rejected preview or apply retains diagnostics and the draft. A committed outcome is shown explicitly even when cleanup also reports an error; it is not offered an ordinary retry. Closing the result after commit dismisses the completed draft.

The Changes page offers full update, precise component update/removal using the inspection’s generation-bound selections, and one full locked restore. It does not choose components by ambiguous display names. Core checks producer ownership and selection editability. The source discovery action resolves the complete currently authored selection in temporary source storage, presents immutable candidates, and uses Core’s captured discovery request for subsequent review. Source changes invalidate that request.

If the preview requires runtime bindings, the confirmation sheet accepts explicit one-time secure inputs, including an intentionally empty value. The immutable input bytes go to Core’s sole synchronous provider during this apply. They are cleared from presentation state on admission, retained only by the owned worker call, and released on completion. They are not written to preferences, diagnostics, inspection or a credential store. Core owns private materialization and file permissions.

Recovery pending disables ordinary modification. Recover and Recheck explicitly enters Core’s writer/recovery boundary without applying new configuration. Recovery and cleanup status remain attached to the original scope, including failures before a callback. A later verified Core observation can resolve Core recovery blocking while retaining the historical diagnostic. The app does not inspect transaction journals or recover another project by interpreting paths.

## Operation lifetime

The application owns a MainActor observable model independently of views. It registers every read, creation, rendering, discovery, preview, apply and recovery operation before admitting it to a serial background OperationQueue. Explicit asynchronous assistance and MCP testing are registered in the same application operation table and retain their Tasks until the actual call and cleanup return; it does not occupy Core’s synchronous queue. Core’s synchronous outer call returns before its completion is delivered to the model. No prepared handle or borrowed source path is retained across actor boundaries.

Cancellation skips queued work while preserving terminal delivery. A running synchronous call remains owned until it returns. A thread-safe admission check immediately before apply linearizes cancellation against starting apply; once apply starts, the app waits for Core’s result. Changing selection invalidates its presentation; diagnostics are still processed against the original scope before the operation is removed. An actual creation result remains attached to its original request. Declaration selection and structural drafts use Core node identities belonging to the captured document generation.

Normal quit and last-window closure go through an AppKit termination delegate. Quit stops admission, cancels queued work and returns `terminateLater` while any operation remains. The delegate replies only after terminal processing. A reported cleanup failure cancels quit and remains visible in diagnostics. Disposition, pre-callback recovery and pending cleanup are processed before selection-generation filtering. Recovery observations are ordered by operation admission so a late older completion cannot clear a newer pending status. The app does not infer transaction state from error text.

## On-device assistance

Settings offers an opt-out preference and displays actual SystemLanguageModel availability on macOS 26 or later. Actions are hidden when disabled or unavailable. A selected managed skill’s public name and description can be explained or translated. A reviewed Core update can be summarized or its configuration changes explained. The change projection includes structural facts only: counts, kinds, missing-state reconstruction and access-change/binding-slot counts. It excludes native values, file contents, paths, source URLs, prompt bodies, binding names and runtime inputs.

Each action first displays its complete selected input for review. Translation accepts an explicit target language. Oversized input is refused before generation. Generate creates one independent on-device LanguageModelSession, with no tools, transcript persistence, chat or cloud fallback. Output is auxiliary selectable/copyable text and never feeds an edit or apply API. Model errors use a fixed safe diagnostic because provider errors may quote input. Cancellation, opt-out, scope changes and quit request Task cancellation but keep ownership until the actual generation returns. Obsolete output is withheld while its safe original-scope failure remains recorded.

The framework is weak-linked for the macOS 15 deployment target and used only behind availability gates. Actual supported-device output quality, translation, cancellation responsiveness, energy and macOS 15 launch require device acceptance. Availability-only evidence or deterministic generation seams do not establish that acceptance. The implementation follows [Apple’s single-turn session guidance](https://developer.apple.com/documentation/foundationmodels/generating-content-and-performing-tasks-with-foundation-models).

## Development validation

The shared scheme isolates its test host through explicit Debug-only test inputs and in-memory preferences. A Debug launch may also supply `--agents-fixture-root <absolute-directory>`; that directory contains `home` and `project` subdirectories prepared by the developer. The launch input does not create fixtures. Release builds ignore these inputs.

Unit tests exercise operation ownership and quit decisions with controlled worker and cleanup timing, stale-selection diagnostics, real Core reads, invalid/orphan configuration, no-write browsing, fixture-only creation and overwrite refusal, real prompt rendering and mappings, typed edit/preview/apply, fingerprint rejection, full restore, source discovery, ephemeral runtime input, source-map presentation, real file-event invalidation and assistance ownership/privacy projection. Unconditional integration failures remain acceptance blockers. UI acceptance uses the designated computer-use surface; the UI-test target is present without a second automation implementation.
